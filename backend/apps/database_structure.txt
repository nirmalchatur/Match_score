  BASE_DIR is the parent of config/, i.e. backend/. The development database
  file is therefore ai-job-agent/backend/db.sqlite3.

  Test database (backend/config/settings_test.py)
    A throwaway SQLite file in the OS temp directory:
        tailorup_apitest.sqlite3   (database + MEDIA_ROOT)
    settings_test.py explicitly refuses a path inside BASE_DIR, so a test run
    can never open the developer's real db.sqlite3.

  Primary key type
    DEFAULT_AUTO_FIELD = "django.db.models.BigAutoField" (settings.py line 83).
    Every project table uses a 64-bit surrogate primary key. Deliberate: an
    AutoField tops out at ~2.1 billion rows, and CI runs `makemigrations
    --check`, which fails while the models.W042 warning is outstanding.

  Time handling
    TIME_ZONE = "UTC", USE_TZ = True. Every DateTimeField is stored in UTC.

  Note on SecurityEvent
  --------------------
  The model class is defined in apps/users/security.py, not models.py, and is
  re-exported at the bottom of apps/users/models.py:

      from .security import SecurityEvent  # noqa: E402,F401

  Django discovers app models by importing <app>.models, so without that
  re-export the table would never be created by a migration. Load-bearing --
  do not "tidy" the import away.

  No ModelAdmin is registered anywhere in the project. The admin site is
  mounted at /admin/ and the tables are created, but no custom admin UI is
  registered for any project model.

                                +-------------------------------------->

  Reading the diagram
  -------------------
  * auth_user is the single tenant root. Every project table hangs off it and
    every one of those links is ON DELETE CASCADE: deleting an account removes
    its jobs, resumes, applications, notifications, preferences, credentials
    and security events in one statement. There is no orphan-by-design.
  * jobs_job <-> resumes_resume is a two-way provenance link:
      - resumes_resume.source_job_id     (which job this was tailored for)
      - resumes_resume.source_resume_id  (which master it was derived from)
  * resumes_resume -> resumes_resumeprofile is 1:1 with CASCADE, so deleting a
    resume always takes its parsed profile with it.
  * applications_application sits at the junction of a user, a job and an
    optional tailored resume. Its own (user_id, job_id) unique constraint is
    what makes the tracker one-row-per-job-per-account.
  * Notifications are leaves apart from their owner; nothing references them.

--------------------------------------------------------------------------------
4.1  auth_user                              (framework: django.contrib.auth)
--------------------------------------------------------------------------------
The identity root. TailorUp deliberately REUSES the built-in User model rather
than swapping in a custom one, and keeps TailorUp-specific preferences in a 1:1
profile (4.2) so a future model swap stays a contained change.

Important: the app's public API is email-based, not username-based. The
register serializer creates the user with `username=email` and `email=email`,
so the two always hold the same value in practice, and sign-in filters on
email. There is NO UNIQUE constraint on email at the database level --
uniqueness is enforced case-insensitively in the serializer only.

  Column          Django type        SQLite        PostgreSQL     Null  Key
  ---------------  -----------------  ------------  -------------  ----  ---
  id              AutoField          integer       integer        no    PK
  password        CharField(128)     varchar(128)  varchar(128)   no
  last_login      DateTimeField      datetime      timestamptz    yes
  is_superuser    BooleanField       bool          boolean        no
  username        CharField(150)     varchar(150)  varchar(150)   no    UQ
  first_name      CharField(150)     varchar(150)  varchar(150)   no
  last_name       CharField(150)     varchar(150)  varchar(150)   no
  email           CharField(254)     varchar(254)  varchar(254)   no
  is_staff        BooleanField       bool          boolean        no
  is_active       BooleanField       bool          boolean        no
  date_joined     DateTimeField      datetime      timestamptz    no

  Constraints
    auth_user_username_key   UNIQUE (username)

  Notes
    * `password` stores a Django password hash, never a plaintext password.
      Hashers in use: PBKDF2 (default) in normal operation; the test settings
      swap in MD5PasswordHasher for speed and must never reach production.
    * `last_login` is NULL until the first successful sign-in.
    * The "legacy" account created by the data migrations (Section 9) is
      username/email "legacy@tailorup.local" with password
      "!unusable-legacy-account". A leading "!" marks the hash unusable in
      Django, so that account can never be signed into until claimed.
    * No role/permission model is used by the application itself. The Group
      and Permission tables exist (admin site) but no code assigns them.

4.2  users_userprofile                      (apps/users/models.py)
--------------------------------------------------------------------------------
Workspace-level settings for one account. 1:1 with auth_user, created on demand
rather than at signup -- an absent row simply means "not onboarded yet".

  Column            Django type                  SQLite          PostgreSQL   Null  Key
  -----------------  ---------------------------  --------------  -----------  ----  ---
  id                BigAutoField                 integer         bigint       no    PK
  user_id           OneToOneField                integer         bigint       no    FK,UQ
  headline          CharField(150)               varchar(150)    varchar(150) no
  discipline        CharField(32)                varchar(32)     varchar(32)  no
  target_locations  CharField(255)               varchar(255)    varchar(255) no
  career_stage      CharField(20)                varchar(20)     varchar(20)  no
  years_experience  PositiveSmallIntegerField    smallint uint   smallint     no
  ai_setup          CharField(20)                varchar(20)     varchar(20)  no
  created_at        DateTimeField(auto_now_add)  datetime        timestamptz  no
  updated_at        DateTimeField(auto_now)      datetime        timestamptz  no

  user_id
    FK  -> auth_user(id)   ON DELETE CASCADE    related_name="profile"
    UNIQUE -- enforced by the OneToOneField: exactly one profile per user.

  Choices (closed sets; Django validates, no DB CHECK is emitted)
    discipline     ENGINEER | DESIGNER | PRODUCT | DATA | MARKETING | OTHER
                   plus "" (blank), which is the default
    career_stage   student | fresher | professional | ""   (lowercase slugs)
    ai_setup       "ollama" (local) | "gemini" (hosted) | ""
                   Free-form varchar(20) with no `choices` tuple, deliberately,
                   so a future provider slug cannot be rejected by the DB layer.

  Defaults
    headline, discipline, target_locations, career_stage, ai_setup = ""
    years_experience = 0    (validators: MinValue 0, MaxValue 60)

  Notes
    * `career_stage` is stored LOWERCASE ("student") while `discipline` is
      stored UPPERCASE ("ENGINEER"). The mismatch is intentional: career
      stage's wire format is the lowercase slug the frontend sends, while
      discipline uses Django's choice keys verbatim. The model exposes
      UserProfile.CAREER_STAGES = ("student", "fresher", "professional").
    * "fresher" is kept separate from "student" on purpose: a final-year
      student has not entered the market, a fresher has and is looking.
    * `years_experience` is an integer, not free text like "5+", so it can be
      compared numerically against the resume parser's output. Stored as 0 for
      students and freshers rather than NULL, so the API always has one shape.
    * `target_locations` is a comma-separated string, not a table: small set,
      always read and written whole, never queried relationally.

  DDL as created by migration (SQLite)
    CREATE TABLE "users_userprofile" (
      "id" integer NOT NULL PRIMARY KEY AUTOINCREMENT,

      "discipline" varchar(32) NOT NULL,
      "target_locations" varchar(255) NOT NULL,
      "created_at" datetime NOT NULL,
      "updated_at" datetime NOT NULL,
      "user_id" integer NOT NULL UNIQUE
        REFERENCES "auth_user" ("id") DEFERRABLE INITIALLY DEFERRED,

    0003_...         + ai_setup, career_stage, years_experience

4.3  users_providercredential                (apps/users/models.py)
--------------------------------------------------------------------------------
A user's own third-party AI provider API key, stored ENCRYPTED. One row per
(user, provider). TailorUp is bring-your-own-key by default: a saved user key
always takes priority over a deployment-wide fallback key.

  Column           Django type        SQLite        PostgreSQL     Null  Key
  ----------------  -----------------  ------------  -------------  ----  ---
  id               BigAutoField       integer       bigint        no    PK
  user_id          ForeignKey         integer       bigint        no    FK
  provider         CharField(32)      varchar(32)   varchar(32)    no
  encrypted_key    TextField          text          text          no
  key_hint         CharField(16)      varchar(16)   varchar(16)    no
  created_at       DateTimeField(auto_now_add) datetime timestamptz  no
  updated_at       DateTimeField(auto_now)     datetime timestamptz  no

  user_id
    FK -> auth_user(id)   ON DELETE CASCADE   related_name="provider_credentials"

  Constraints
    uniq_user_provider_credential   UNIQUE (user_id, provider)
    A user holds at most one key per provider, which lets the save path be an
    unconditional UPDATE rather than a lookup-then-branch.

  Indexes
    users_providercredential_user_id_...   (user_id)   [automatic FK index]

  Security notes -- the most sensitive table in the schema
  ---------------------------------------------------
    * `encrypted_key` holds a Fernet token produced by apps/users/crypto.py.
      The PLAINTEXT key is never stored, never returned by any API, and never
      logged. Uses the Fernet symmetric construction from `cryptography`
      50.0.1, keyed from SECRET_KEY-derived material.
    * `key_hint` is a masked 4+4 character prefix/suffix such as
      "AIza...4f2b", written once at save time. It exists purely so the UI can
      show WHICH key is stored when a user juggles more than one. It is NOT a
      secret and cannot be scaled back into the key.
    * `reveal_key()` decrypts for immediate use only. If decryption fails it
      DELETES the row and re-raises, because a key that cannot be decrypted
      looks configured but silently fails at call time; deleting it lets the
      user re-paste and see an honest "not configured".
    * `public_dict()` is the only shape any endpoint may return, and it
      contains no field from which the key could be recovered.
    * Changes are recorded as a SecurityEvent of type AI_KEY_CHANGED (4.4),
      never the key itself.

  DDL as created by migration (SQLite)
    CREATE TABLE "users_providercredential" (
      "id" integer NOT NULL PRIMARY KEY AUTOINCREMENT,
      "provider" varchar(32) NOT NULL,
      "encrypted_key" text NOT NULL,
      "key_hint" varchar(16) NOT NULL,
      "created_at" datetime NOT NULL,
      "updated_at" datetime NOT NULL,
      "user_id" integer NOT NULL
        REFERENCES "auth_user" ("id") DEFERRABLE INITIALLY DEFERRED,
      CONSTRAINT "uniq_user_provider_credential" UNIQUE ("user_id","provider")
    );

  `provider` values in use: "gemini", "groq". "ollama" needs no key and so
  never produces a row here.
  Column provenance: 0002_providercredential -- all columns.

4.4  users_securityevent                     (apps/users/security.py)
--------------------------------------------------------------------------------
A short, append-only record of authentication-relevant things that happened to
one account: sign-ins, sign-outs, password changes, session revocations, and AI
key changes. This is NOT a general audit log -- it is scoped to the owner and
never records another account's IP, a token value, or a key.

  Column               Django type        SQLite        PostgreSQL     Null  Key
  --------------------  -----------------  ------------  -------------  ----  ---
  id                   BigAutoField       integer       bigint        no    PK
  user_id              ForeignKey         integer       bigint        no    FK
  event                CharField(32)      varchar(32)   varchar(32)    no
  user_agent           CharField(300)     varchar(300)  varchar(300)   no
  is_current_session   BooleanField       bool          boolean        no
  created_at           DateTimeField(auto_now_add) datetime timestamptz  no

  user_id
    FK -> auth_user(id)   ON DELETE CASCADE   related_name="security_events"

  event (closed choices)
    LOGIN_SUCCESS     Signed in
    LOGOUT            Signed out
    PASSWORD_CHANGED  Password changed
    SESSIONS_REVOKED  Other sessions signed out
    AI_KEY_CHANGED    API key updated

  Meta
    ordering = ["-created_at", "-id"]

  Indexes
    secevent_user_time_idx   (user_id, created_at DESC)
    Supports the "recent security activity" list, newest first.

  Notes
    * `user_agent` is coarse client context, HARD TRUNCATED to 300 characters.
      It comes from a request header an attacker controls, so it is untrusted
      input: never rendered back as markup, never used to build a link.
    * `is_current_session` is computed at WRITE time from the session key, so
      a later "sign out other devices" cannot retroactively change what the
      owner was shown.
    * Recording never raises. It is called from inside the login and logout
      paths, and a failure to write a log line must not turn a successful
      sign-in into a 500.
    * A FAILED sign-in produces NO row, because there is no user to attach it
      to; attaching it to a guessed account would leak that the account exists
      and fill a stranger's log with someone else's attempts. Failed attempts
      are handled by the auth throttle instead.

  Sessions -- no separate table
  -----------------------------
  There is no "active sessions" table. The security page reads Django's own
  `django_session` table (4.18) and decodes each row's session_data to find
  `_auth_user_id`, so the list always reflects REAL, live sessions and
  "sign out everywhere else" revokes exactly the rows the auth middleware
  consults. A parallel table would drift from reality the first time a session
  expired or was cleared.

  Column provenance: 0004_securityevent -- all columns.

4.5  jobs_job                               (apps/jobs/models.py)
--------------------------------------------------------------------------------
One job posting the user has saved and/or analysed against their master resume.
Every job belongs to exactly one account: `user_id` is the tenant boundary and
API queries must ALWAYS be scoped by it.

  Column           Django type        SQLite        PostgreSQL      Null  Key
  ----------------  -----------------  ------------  --------------  ----  ---
  id               BigAutoField       integer       bigint         no    PK
  user_id          ForeignKey         integer       bigint         no    FK
  url              URLField           varchar(200)  varchar(200)   no
  company          CharField(255)     varchar(255)  varchar(255)   no
  title            CharField(255)     varchar(255)  varchar(255)   no
  source           CharField(32)      varchar(32)   varchar(32)    no
  location         CharField(255)     varchar(255)  varchar(255)   no
  description      TextField          text          text           no
  match_score      FloatField         real          double precision yes
  match_result     JSONField          text (JSON)   jsonb          yes
  decision         CharField(50)      varchar(50)   varchar(50)    no
  status           CharField(50)      varchar(50)   varchar(50)    no
  error_message    TextField          text          text           no
  pipeline_steps   JSONField          text (JSON)   jsonb          no
  created_at       DateTimeField(auto_now_add) datetime timestamptz  no
  updated_at       DateTimeField(auto_now)     datetime timestamptz  no

  user_id
    FK -> auth_user(id)   ON DELETE CASCADE   related_name="jobs"
    THE tenant boundary. Scoped per owner so two different users can analyse
    the same posting independently.

  url
    URLField, max_length defaults to 200. Stored WITHOUT a unique constraint
    of its own; uniqueness is the composite below. Migration 0004 changed this
    from a global UNIQUE url to a per-account UNIQUE (user_id, url).

  Constraints
    unique_job_url_per_user   UNIQUE (user_id, url)
    Prevents duplicate job postings per account, while still allowing the same
    URL to be analysed independently by different users.

  Indexes
    jobs_job_user_id_...   (user_id)   [automatic FK index]
    Meta ordering = ["-created_at"]

  status (8 values -- a superset spanning two generations)
    PENDING     Pending     -- default; queued, not started
    RUNNING     Running     -- analysis in progress
    COMPLETED   Completed   -- analysis finished WITH a match score
    READY       Ready       -- analysis finished but no score produced
    FAILED      Failed      -- analysis errored; see error_message
    NEW / PROCESSING / READY / SKIPPED  -- legacy values retained so historical
    rows keep rendering. Django does NOT emit a database CHECK for `choices`;
    the constraint is application-level.

  decision (closed set, blank = not yet decided)
    USE_MASTER   Use Master Resume
    TAILOR       Tailor Resume
    SKIP         Skip
    REVIEW       Review

  source
    Which ATS the posting was read from: "greenhouse", "workday", "lever",
    "generic", and whatever is added later. Written by the ATS registry at
    analyse time and read by the UI to pick a badge. Defaults to "generic"
    rather than blank so a row saved before this field existed still renders
    sensibly, and so the column is never NULL -- the UI would otherwise have
    to special-case it.

  JSON columns
    match_result    nullable. The full MatchEngine output. See Section 8.1.
    pipeline_steps  NOT NULL, default []. A list of
                    {"name": str, "status": "complete"|"running"|"pending"}
                    dicts showing pipeline progress for the UI. Overwritten
                    wholesale on each transition; see Section 8.3.

  Notes
    * `match_score` is a plain float, 0-100, duplicated from
      match_result["score"]. Kept as a real column so the workspace can sort
      and filter on it in SQL without parsing JSON on every request.
    * `error_message` holds a human-readable failure reason, surfaced in the
      API. It must never contain a stack trace or a provider API key.
    * `location` and `description` are blank-able at the model level but the
      columns are NOT NULL with a "" default, so the API always returns a
      string.

  DDL as created by migration (SQLite)
    CREATE TABLE "jobs_job" (
      "id" integer NOT NULL PRIMARY KEY AUTOINCREMENT,
      "url" varchar(200) NOT NULL,
      "company" varchar(255) NOT NULL,
      "title" varchar(255) NOT NULL,
      "location" varchar(255) NOT NULL,
      "description" text NOT NULL,
      "match_score" real NULL,
      "decision" varchar(50) NOT NULL,
      "status" varchar(50) NOT NULL,
      "created_at" datetime NOT NULL,
      "updated_at" datetime NOT NULL,
      "match_result" text NULL
        CHECK ((JSON_VALID("match_result") OR "match_result" IS NULL)),
      "error_message" text NOT NULL,
      "pipeline_steps" text NOT NULL
        CHECK ((JSON_VALID("pipeline_steps") OR "pipeline_steps" IS NULL)),
      "user_id" integer NOT NULL
        REFERENCES "auth_user" ("id") DEFERRABLE INITIALLY DEFERRED,
      "source" varchar(32) NOT NULL,
      CONSTRAINT "unique_job_url_per_user" UNIQUE ("user_id","url")
    );
    SQLite enforces JSON validity through the JSON_VALID CHECK emitted by
    Django's JSONField. PostgreSQL gets a native `jsonb` type, which validates
    natively and could be GIN-indexed if that is ever needed.

  Column provenance
    0001_initial   id, url (initially globally unique), company, title,
                   location, description, match_score, decision, status,
                   created_at, updated_at
    0002           + match_result
    0003           + error_message, + pipeline_steps, status choices widened,
                   default changed to PENDING
    0004           + user (nullable, backfilled, then made NOT NULL), url
                   uniqueness relaxed to (user_id, url), ordering added
    0005           + source

4.6  resumes_resume                         (apps/resumes/models.py)
--------------------------------------------------------------------------------
A resume document. Two kinds share this one table, distinguished by
`resume_type`: a MASTER resume (the uploaded original) and a TAILORED version
(an AI-generated rewrite of a master, targeting one job).

A tailored resume is NEVER an edit of the master. It is a NEW row that points
back at the document it was derived from, so the master can never be
overwritten and the lineage stays inspectable.

  Column             Django type        SQLite        PostgreSQL     Null  Key
  -----------------  -----------------  ------------  -------------  ----  ---
  id                 BigAutoField       integer       bigint        no    PK
  user_id            ForeignKey         integer       bigint        no    FK
  name               CharField(255)     varchar(255)  varchar(255)   no
  file               FileField          varchar(100)  varchar(100)   no
  resume_type        CharField(20)      varchar(20)   varchar(20)    no
  is_master          BooleanField       bool          boolean        no
  profile_data       JSONField          text (JSON)   jsonb          yes

4.7  resumes_resumeprofile                  (apps/resumes/models.py)
--------------------------------------------------------------------------------
The structured, parsed content of one resume. Strictly 1:1 with
resumes_resume, and owned by it: deleting a resume always deletes its profile.

This table exists so the analysis engine and the document generator can read a
resume as data (skills list, parsed roles, sections) without re-parsing the

  education        TextField          text          text           no
  projects         TextField          text          text           no
  certifications   TextField          text          text           no
  created_at       DateTimeField(auto_now_add) datetime timestamptz  no
  updated_at       DateTimeField(auto_now)     datetime timestamptz  no

  resume_id
    FK -> resumes_resume(id)   ON DELETE CASCADE   related_name="profile"

  row rather than NULL. See Section 8.5 for the full shapes.

  skills vs qualities -- the important distinction
  ------------------------------------------------

  `qualities` is CHOSEN: deliberate claims the user makes about themselves.

  whereas a chosen quality is an assertion and must be validated.

  always read and written whole, and never queried relationally. A table would
  buy nothing here and would make the "select up to N" UI awkward.
  The catalogue is 50 curated options across 7 groups (programming,
  data_structures, problem_solving, soft_skills, project_management,
  leadership, hr); the user picks exactly 7, and validate_selection()
  enforces a minimum server-side.

4.9  automation_notification                 (apps/automation/models.py)
--------------------------------------------------------------------------------
One thing that happened, worth telling the user about. A ROW per notification,
not a counter: a count cannot say "your tailoring finished" and is useless the
moment a user wants to know what they missed. The list is the feature; the
unread dot is a convenience derived from it.

Read state lives on the row. An is_read boolean plus an index makes the unread
count one indexed query rather than a scan, and "mark all read" a single
UPDATE. A separate read-tracking table would be more normalised and would buy
nothing at this scale.

  Column         Django type        SQLite        PostgreSQL     Null  Key
  --------------  -----------------  ------------  -------------  ----  ---
  id             BigAutoField       integer       bigint        no    PK
  user_id        ForeignKey         integer       bigint        no    FK
  kind           CharField(16)      varchar(16)   varchar(16)    no
  title          CharField(120)     varchar(120)  varchar(120)   no
  body           TextField          text          text           no
  link           CharField(255)     varchar(255)  varchar(255)   no
  is_read        BooleanField       bool          boolean        no
  dedupe_key     CharField(120)     varchar(120)  varchar(120)   no
  created_at     DateTimeField(auto_now_add) datetime timestamptz  no
  read_at        DateTimeField      datetime      timestamptz    yes

  user_id
    FK -> auth_user(id)   ON DELETE CASCADE   related_name="notifications"
    A notification records an event about someone's job search and must never
    be visible to anyone else. Scoped on `user` on every query.

  kind (closed set, default INFO)
    INFO      Information
    SUCCESS   Success
    WARNING   Warning
    ERROR     Error
    A closed set rather than free text because the frontend maps these to an
    icon and a tone; an unknown value would have no presentation and would
    render as a blank row.

  title
    One line -- the notification is skimmable from this alone. The writer
    truncates to 120 chars (title[:120]) because the DB max_length is not a
    reliable guard on every backend.

  link -- SECURITY-CRITICAL
    Where the UI should send the user on click, e.g. "/app/jobs?job=12".
    Stored as a PATH, never a full URL, and rendered through client-side
    navigation. This is deliberate: an attacker who can write a notification
    row must not be able to turn it into an off-site (phishing) redirect.
    Truncated to 255 chars by the writer.

  dedupe_key
    Natural key for de-duplication. EMPTY ("") for notifications that should
    never repeat (a one-off warning); SET for ones a poller could emit
    repeatedly (e.g. "analysis finished", keyed by job id). Truncated to 120.

  read_at
    NULL while unread. Set alongside is_read by mark_read(). Redundant with
    is_read by design: is_read is the flag the index serves, read_at is the
    human-facing timestamp.

  Constraints
    uniq_notification_dedupe   UNIQUE (user_id, kind, dedupe_key)
                               WHERE dedupe_key > ''      (partial index)
    CONDITIONAL, and that condition is the whole point: only rows that opted
    into de-duplication participate. A plain unique constraint on a blank
    string would permit exactly ONE empty-key row per (user, kind), which is
    the precise opposite of what "" is meant to mean.
    Partial unique constraints are supported by SQLite (since 3.8.0) and
    PostgreSQL, so this behaves identically on both backends.

  Indexes
    notif_unread_idx     (user_id, is_read, created_at DESC)
        Serves the bell's unread count on every page load.
    notif_user_time_idx  (user_id, created_at DESC)
        Serves the notification list itself.

  Meta
    ordering = ["-created_at", "-id"]    (id breaks ties on identical
                                          timestamps so paging is stable)

  Notes
    * `Notification.notify()` is the only intended constructor. It returns
      None on a de-duplicated repeat rather than raising, so a call site
      inside a request never has to know whether it is the first to see the
      event. The IntegrityError catch covers the race the pre-check cannot:
      two requests can both find no row and both try to insert; the
      constraint makes the second fail, and failing INTO the desired state is
      a success, not an incident to log.
    * `mark_read()` is idempotent: it returns False and does NOT touch read_at
      if the row is already read, so "mark all read" and the per-row path can
      both reach the same notification without the second overwriting the
      original read time.

  DDL as created by migration (SQLite)
    CREATE TABLE "automation_notification" (
      "id" integer NOT NULL PRIMARY KEY AUTOINCREMENT,
      "kind" varchar(16) NOT NULL,
      "title" varchar(120) NOT NULL,
      "body" text NOT NULL,
      "link" varchar(255) NOT NULL,
      "is_read" bool NOT NULL,
      "dedupe_key" varchar(120) NOT NULL,
      "created_at" datetime NOT NULL,
      "read_at" datetime NULL,
      "user_id" integer NOT NULL
        REFERENCES "auth_user" ("id") DEFERRABLE INITIALLY DEFERRED
    );
    CREATE UNIQUE INDEX "uniq_notification_dedupe"
      ON "automation_notification" ("user_id","kind","dedupe_key")
      WHERE "dedupe_key" > '';

4.10 automation_notificationpreference       (apps/automation/models.py)
--------------------------------------------------------------------------------
Per-user switches for which notifications get created. A MODEL rather than a
settings default because the choice is personal and has to travel with the
account.

An ABSENT row means "all defaults on", so signup does not have to write a row
for every user. `for_user()` does get_or_create on first access.

  Column                Django type    SQLite        PostgreSQL    Null  Key
  ---------------------  -------------  ------------  -----------  ----  ---
  id                    BigAutoField   integer       bigint       no    PK
  user_id               OneToOneField  integer       bigint       no    FK,UQ
  job_updates           BooleanField   bool          boolean       no
  job_matches           BooleanField   bool          boolean       no
  application_updates   BooleanField   bool          boolean       no
  updated_at            DateTimeField(auto_now) datetime  timestamptz  no

  user_id
    FK -> auth_user(id)   ON DELETE CASCADE
    related_name="notification_preferences"
    UNIQUE -- exactly one preference row per user.

  Switches (all default True)
    job_updates           Tell me when a job finishes analysing or tailoring.
    job_matches           Tell me when a new analysed job scores well against
                          my resume.
    application_updates   Tell me when an application changes stage.

  Meta
    verbose_name_plural = "notification preferences"

  The `allows(kind)` rule -- the interesting logic on this model
  ------------------------------------------------------------------
  `allows()` maps a notification KIND onto the switches, and the mapping is
  not 1:1:

      kind == ERROR   -> job_updates OR application_updates
      kind == SUCCESS -> job_updates OR job_matches
      anything else   -> job_updates

  A failure is suppressed only when the user has switched off *every* category
  that could produce it. Turning off job updates while leaving application
  updates on should not silence an analysis error: the user still wants to hear
  that something broke, they just do not want a note every time a job is
  re-scored.

  UNKNOWN KINDS ARE ALLOWED rather than dropped. A kind added by a later
  release should reach users, and an absent preference row is a configuration
  default, not a reason to silently swallow an event.

  Note: this logic lives in Python. Nothing in the database enforces it, so a
  raw SQL INSERT can create notifications the user has switched off. That is
  acceptable -- notifications are advisory -- but do not mistake the booleans
  for an access-control mechanism.

  Column provenance: automation/0001_initial -- all columns (single migration).

4.18  django_session                        (django.contrib.sessions)
--------------------------------------------------------------------------------
READ DIRECTLY BY APPLICATION CODE -- see apps/users/security.py.

  session_key    CharField(40)   PK   (NOT an auto-increment id)
  session_data   TextField       NOT NULL
  expire_date    DateTimeField   NOT NULL
  Index  django_session_expire_date_...  (expire_date)
        Used to find expired rows to purge and to list live sessions.

  * SESSION_ENGINE is not overridden, so this is Django's default DB-backed
    engine. Switching to a cache or signed-cookie backend would BREAK the
    "active sessions" security page, which enumerates real rows.
  * session_data is a base64-encoded, signed, zlib-compressed pickle. The
    security page decodes it and reads `_auth_user_id` to attribute a session
    to an account. A row that fails to decode is SKIPPED, never guessed at:
    deleting every unidentifiable session would be a denial-of-service lever,
    and deleting every identifiable one is the correct behaviour.
  * The session_key IS a secret. It is returned to the account it belongs to,
    over an authenticated request, only so "sign out this device" has
    something to name.
  * "Sign out everywhere else" DELETES the rows. Because Django consults the
    session store on every authenticated request, this revokes a stolen session
    IMMEDIATELY rather than at an expiry an attacker could wait out.
  * `change_password()` calls update_session_auth_hash() so the CURRENT session
    survives a password change. Django stores a hash of the password inside
    the session; changing it without re-hashing would sign the account out of
    the very tab used to make the change, which reads as a bug.

5.3  NOTABLE ABSENCES (things you might expect and should not assume)
--------------------------------------------------------------------------------
  * No index on jobs_job.status, match_score, or created_at. Queries filter by
    user_id first, so the user_id index is the one that matters at this scale.
    If a cross-user "top matches" feature is added, add a composite
    (user_id, match_score DESC) index at that point.
  * No index on any JSON column. Correct as designed: nothing queries inside
    the JSON payloads, they are always read whole.
  * No index on resumes_resume.is_master. The master lookup goes through
    user_id, and a user has a handful of resumes.
  * No full-text index on jobs_job.description or any resume text. Job search
    is performed by the ORM in Python today.

7.1  WHAT HAPPENS WHEN A ROW IS DELETED
--------------------------------------------------------------------------------
  Deleted row                     Cascades to                     Sets NULL in
  ------------------------------  ------------------------------  -----------------
  auth_user (an account)          users_userprofile              (nothing)
                                  users_providercredential
                                  users_securityevent
                                  jobs_job
                                  resumes_resume
                                  applications_application
                                  automation_notification
                                  automation_notificationpreference
                                  (django_session is not an FK --
                                   rows are found by decoding
                                   session_data and deleted by
                                   security.py)

  jobs_job                        applications_application        resumes_resume
                                                                .source_job_id
                                  (CASCADE)                       (SET NULL)

  resumes_resume                  resumes_resumeprofile           resumes_resume
                                                                .source_resume_id
                                  (CASCADE)                       (SET NULL)

                                                                applications_
                                                                application
                                                                .tailored_resume_id
                                                                (SET NULL)

  automation_notification         nothing
  automation_notificationpref.    nothing

  Reading the set of rules
  ------------------------
  Deleting a MASTER resume does NOT delete the tailored resumes made from it
  -- it only clears their source_resume_id pointer. The tailored documents
  survive as first-class resumes; only their provenance annotation is lost.

  Deleting a JOB does NOT delete tailored resumes made for it -- it only
  clears source_job_id. The generated content outlives the posting.

  Deleting a JOB DOES delete its application rows, because an application
  without a job is meaningless, and the job row only exists as long as its
  owner does anyway.

  Deleting an ACCOUNT removes everything belonging to it, in one statement.
  There is no separate "anonymise" or "soft delete" path in the schema.

7.2  THE TENANT-ISOLATION RULE
--------------------------------------------------------------------------------
  Every project table carries a `user_id` FK to auth_user, and every one of
  those links is ON DELETE CASCADE. `user_id` is therefore simultaneously:

    1. The authorisation boundary. API queries must ALWAYS be scoped by it.
       A query that forgets the filter returns another candidate's private job
       analysis, which is a data breach, not a display bug.
    2. The deletion mechanism. Because it cascades, account removal is a
       single DELETE and there is no orphan cleanup job to get wrong.

  Tables that carry the boundary
      users_userprofile                  (via user_id, 1:1)
      users_providercredential           (via user_id)
      users_securityevent                (via user_id)
      jobs_job                           (via user_id)
      resumes_resume                     (via user_id)
      resumes_resumeprofile              (INDIRECTLY, via resume_id --
                                          it has no user_id of its own)
      applications_application           (via user_id)
      automation_notification            (via user_id)
      automation_notificationpreference  (via user_id)

  IMPORTANT -- resumes_resumeprofile has NO user_id column.
  It reaches a tenant only through resumes_resumeprofile.resume_id ->
  resumes_resume.id -> resumes_resume.user_id. Any query against a profile
  MUST traverse to the parent resume and filter on ITS user_id. Writing
  `ResumeProfile.objects.all()` unscoped would return every user's parsed
  resume content.

  Deliberate secondary boundaries
      jobs_job              (user_id, url) UNIQUE
      applications_application (user_id, job_id) UNIQUE
  These are scoped per account, NOT globally, so two users can independently
  track the same job posting.

7.3  THE `read_at` / `applied_at` WRITE RULES
--------------------------------------------------------------------------------
  Two timestamps are set by MODEL methods rather than by views, so the rule
  holds no matter which endpoint caused the change:

    Application.mark_applied(when=None)
        Stamps applied_at on the transition into APPLIED / ASSESSMENT /
        INTERVIEW / OFFER, guarded by `and not self.applied_at`, so the
        ORIGINAL submission time is never overwritten by a later status edit.

    Notification.mark_read()
        Idempotent: returns False and does NOT touch read_at if already read,
        so the per-row path and the "mark all read" path can both reach the
        same row without the second clobbering the first read time.

================================================================================
8.  JSON PAYLOAD SCHEMAS
================================================================================
Six JSONField columns store structured documents. They are NOT queryable in
this application -- always read whole. This section documents their shapes so
a future change does not silently break a consumer.

8.1  jobs_job.match_result  (nullable object)
--------------------------------------------------------------------------------
Written by apps/jobs/services/match_engine.py (MatchEngine.calculate).
The complete, self-describing output of one match computation. Because it is
the authority for the skill-gap view, the UI can never disagree with the score.

  {
    "score":       float,                    # 0-100, round(x, 2)
    "skills":      { ... },                  # weighted 0.50
    "experience":  { ... },                  # weighted 0.20
    "requirements":{ ... },                  # weighted 0.20
    "education":   { ... },                  # weighted 0.10
    "qualities":   { ... },                  # REPORTED, NEVER SCORED
    "decision":    "USE_MASTER"|"TAILOR"|"SKIP"|"REVIEW"
  }

  The four weights sum to 1.00. `qualities` is deliberately excluded from the
  score: a user-asserted quality is not evidence, and letting it move the
  number would make the score unfalsifiable.

  skills       {"score": float,
                "matched": [normalized skill names],
                "missing": [normalized skill names]}
              Names come from the ONE shared catalog in
              apps/resumes/services/skill_catalog.py, normalized to
              lowercase by SkillNormalizer. The UI displays the catalog's
              display form, not the stored lowercase.

  experience   {"score": float,
                "required_years":  float,
                "candidate_years": float,
                "note": str}
              An empty JD returns score 100.0 -- no requirement means no
              penalty, not a zero.

  requirements {"score": float,
                "matched": [raw requirement LINES],
                "partially_matched": [raw requirement LINES],
                "unmatched": [raw requirement LINES]}
              These are raw JD requirement lines (e.g. "3+ years with
              Docker"), NOT catalog skills. Partial credit is recorded
              against the sentence. apps/jobs/services/skill_gap.py reduces
              partially_matched to catalog skills at READ time, because
              showing the raw sentence in a panel titled "Skill analysis"
              made non-skills appear as missing skills.

  education    {"score": float, ...}

  qualities    {"matched": [...], "selected": [...], "note": str}
              When nothing is selected: matched=[], selected=[],
              note="No qualities selected".

  Known-fragility note: jobs/tests/test_job_search.py deliberately writes the
  string "not-a-dict" into match_result and asserts the app survives it. The
  READ path must tolerate a non-dict here (`job.match_result or {}` plus
  .get() calls). Any new consumer of this column should do the same.

8.2  resumes_resume.profile_data  (nullable object)
--------------------------------------------------------------------------------
Two different shapes depending on resume_type. There is no discriminator field
inside the JSON -- use the `resume_type` COLUMN, not the payload, to tell them
apart.

  (a) resume_type = "MASTER" -- the output of ResumeProfileService.build(text),
      i.e. what the parser extracted from the uploaded document:
      {
        "skills":         [normalized skill names],
        "experience":     { ... }   # ExperienceParser output
        "education":      str,
        "projects":       str,
        "certifications": str
      }

  (b) resume_type = "TAILORED" -- the AI payload verbatim (the same object
      stored under tailoring_result["result"]). So for a tailored resume,
      profile_data IS the generated content, which is why the existing
      list/detail endpoints can serve a tailored version with no document
      generator in the read path.

8.3  jobs_job.pipeline_steps  (NOT NULL list, default [])
--------------------------------------------------------------------------------
Pipeline progress for the UI. Each element is {"name": str, "status": str}.

  status is one of: "complete" | "running" | "pending"

  The list is REPLACED WHOLESALE on each transition -- it is not appended to.
  The analyse endpoint writes a 6-step list with steps 1-3 complete, step 4
  running and steps 5-6 pending, then overwrites it with an 8-step all-complete
  list on success.

  Because the list is replaced rather than extended, a consumer must treat the
  step NAMES as the contract, not their positions: the in-flight list has six
  entries and the settled list has eight, and they are not aligned.

8.4  resumes_resume.tailoring_result  (nullable object, TAILORED rows only)
--------------------------------------------------------------------------------
Written by the save-tailoring endpoint in apps/resumes/views.py.

  {
    "result":     { ... },   # the AI payload == profile_data for this row
    "validation": { ... },   # the validation verdict
    "source":     { ... }    # the re-derived source resume view
  }

  Why it is kept separately from profile_data, when the two overlap:
  profile_data exists so the row behaves like a normal resume to the rest of
  the app. tailoring_result exists so a saved version can ALWAYS be explained
  after the fact -- including why the validator accepted it. The "source"
  member is re-derived from the stored master rather than taken from the
  request, so a saved version is self-describing and cannot be told to
  believe a client-supplied "original".

  A tailoring that FAILS validation is never written to the database at all:
  the endpoint returns HTTP 422 with code "ai_validation_failed" and a
  violations list. There are no rejected tailoring rows to clean up.

8.5  resumes_resumeprofile JSON columns
--------------------------------------------------------------------------------
  skills       list[str]   default []
      Normalized against the shared catalog by SkillNormalizer. PARSED
      evidence -- whatever the extractor found in the document.

  experience   object      default {}
      Shape produced by ExperienceParser; consumed as
      (profile["experience"] or {}).get("roles") -> [ ... ]. The stored
      profile is the authority on HOW MANY roles exist; the tailoring only
      ever rewrites them, by position, using ids of the form "exp-0",
      "exp-1", ... So a consumer must index rather than match by id.

  qualities    object      default {}
      Group key -> list, e.g. {"technical": [...], "soft_skills": [...]}
      CHOSEN claims, as opposed to the parsed `skills` above. Server-side
      minimum of 7 from a 50-entry catalogue across 7 groups; the picker also
      requires at least one from every group, so a selection cannot be seven
      programming languages and nothing else. See apps/resumes/qualities.py.

      NOTE: the KINDS in apps/resumes/qualities.py are
      (programming, data_structures, problem_solving, soft_skills,
       project_management, leadership, hr) -- SEVEN group keys -- while the
      MODEL FIELD's docstring shows a three-key example
      ({"technical", "project_management", "soft_skills"}). The docstring is
      illustrative and out of date; the module-level KINDS tuple is the
      authority. Treat the stored dict as "group key -> list" and do not
      hard-code either list of group names when reading it.

8.6  NOT STORED IN THE DATABASE (worth stating explicitly)
--------------------------------------------------------------------------------
  These all live on disk or in config, and someone will eventually ask:
    * Uploaded resume FILES are on the filesystem under MEDIA_ROOT, referenced
      only by resumes_resume.file (a relative path string).
    * Generated DOCX/PDF documents are produced on demand from
      profile_data + tailoring_result and are not persisted.
    * The candidate's raw resume TEXT is not stored; only its parsed profile.
    * AI provider API keys are stored ONLY in users_providercredential.
      encrypted_key, as a Fernet token. No key is ever written to a job row,
      a resume row, a notification, or a log line.
    * The per-request "source" view sent to the AI is derived on the fly and
      is not persisted, except where copied into tailoring_result["source"].

9.2  THE TWO DATA-PRESERVING OWNERSHIP MIGRATIONS -- read before touching
--------------------------------------------------------------------------------
  jobs/0004_job_user_ownership and resumes/0004_resume_user_ownership added
  per-account ownership to tables that predated accounts. Both use the same
  three-step shape, and the ordering is not optional:

    1. AddField the FK as NULLABLE, so existing rows are untouched.
    2. RunPython backfill: claim every pre-ownership row for a single "legacy"
       holder account, created with get_or_create.
    3. AlterField to NOT NULL, enforcing ownership.
  plus, for jobs only: relax url from globally-unique to (user_id, url).

  The legacy account is username/email "legacy@tailorup.local" with password
  "!unusable-legacy-account". The leading "!" marks the hash unusable in
  Django, so it can never be signed into until claimed manually.

  Why backfill rather than delete: these rows are real user analyses and real
  uploaded resumes. Deleting them would orphan historical work; claiming them
  keeps everything intact and visible. Both migrations ship a REVERSE function
  (clear_owner) that sets user back to NULL.

9.3  THE ONE HAND-WRITTEN MIGRATION -- and why
--------------------------------------------------------------------------------
  resumes/0007_resumeprofile_qualities is deliberately NOT generated. Its own
  comment records the reason:

    `makemigrations` on the development machine also wanted to rewrite the
    primary keys of Resume and ResumeProfile from BigAutoField down to
    AutoField, because the local interpreter resolves the implicit `id`
    differently from the pinned Django 6.1 that CI and Render run. Committing
    that would silently narrow every id column in production on a live table.
    Only the field this feature adds is wanted here; the primary keys stay as
    0001_initial created them.

  Practical consequence: if you regenerate migrations on a machine whose
  Django version differs from the pinned 6.1.1, you will see spurious
  AlterField operations for primary keys. Review generated migrations BEFORE
  committing, and keep the pin in requirements.txt authoritative.

9.4  SAFELY CHANGING THE SCHEMA
--------------------------------------------------------------------------------
  cd ai-job-agent/backend
  python manage.py makemigrations                  # generate
  python manage.py migrate                         # apply to dev SQLite
  python manage.py makemigrations --check --dry-run   # what CI runs

  Rules this project actually depends on:
    * NEVER write a migration by hand that narrows a primary key.
      BigAutoField -> AutoField on a live table is a silent production
      regression, which is exactly what 9.3 exists to prevent.
    * Widen, never narrow, a max_length. The project says this explicitly
      where it sets DEFAULT_AUTO_FIELD.
    * Adding a NOT NULL column to a populated table needs a default or a
      three-step add-backfill-alter like 9.2. A bare AddField NOT NULL will
      fail or lock a real PostgreSQL table.
    * Adding a column with `choices=` requires a migration, because Django
      records choices in migration state even though the DB has no CHECK.
    * Deleting a column leaves the data in PostgreSQL until the column is
      dropped for real. Write an explicit RemoveField.
    * CI runs `makemigrations --check`; an uncommitted migration fails the
      build, as does models.W042 (any model without an explicit primary key).


================================================================================
10.  SECURITY POSTURE ENFORCED IN THE DATA MODEL
================================================================================

10.1  CREDENTIALS AT REST
--------------------------------------------------------------------------------
  users_providercredential.encrypted_key holds a Fernet token produced by
  apps/users/crypto.py. The plaintext key is never stored, never returned by
  any API, and never logged. key_hint is a 4+4 character mask written once at
  save time; it is not a secret and cannot be scaled back into a key.
  `reveal_key()` deletes a row it cannot decrypt, because a key that looks
  configured but silently fails at call time is worse than an honest
  "not configured".

  The `cryptography` pin is 50.0.1, deliberately: 44.x carries ten known
  advisories, and this package guards every stored credential. The dependency
  audit in CI fails the build on them.

10.2  NO SECRET EVER REACHES ANOTHER COLUMN
--------------------------------------------------------------------------------
  AI keys live in exactly one place. They are not copied into
  users_securityevent, automation_notification, jobs_job.error_message, or any
  resume row. Key changes are recorded as an event TYPE (AI_KEY_CHANGED), and
  a failed sign-in records NO row at all.

10.3  NOTIFICATION LINKS CANNOT BECOME AN OPEN REDIRECT
--------------------------------------------------------------------------------
  automation_notification.link stores a PATH ("/app/jobs?job=12"), never a
  full URL, and the frontend navigates client-side. An attacker who can write
  a notification row therefore cannot turn it into an off-site redirect.
  Anything you add to this column must preserve that property.

10.4  UNTRUSTED INPUT IS STORED, NEVER INTERPRETED
--------------------------------------------------------------------------------
  users_securityevent.user_agent comes from a request header an attacker
  controls. It is truncated to 300 characters, never rendered as markup, and
  never used to build a link. Treat any new column in this table the same way.

10.5  SESSION REVOCATION IS REAL, NOT BOOKKEEPING
--------------------------------------------------------------------------------
  "Sign out everywhere else" DELETES django_session rows. Because Django
  consults the session store on every authenticated request, a stolen session
  stops working IMMEDIATELY rather than at an expiry an attacker could wait
  out. A row that fails to decode is skipped, never guessed at -- deleting
  every unidentifiable session would be a denial-of-service lever, and
  deleting every identifiable one is correct.

  change_password() calls update_session_auth_hash() so the CURRENT session
  survives, and the security page is explicit that a password change alone
  does not tell a user whether another session was invalidated -- which is
  the reason the session list exists at all.

10.6  AUDIT SCOPE
--------------------------------------------------------------------------------
  users_securityevent is NOT a general audit log. It records
  authentication-relevant events for THIS account only, and never another
  account's IP address, a token value, or a key. NotificationPreference
  booleans are preferences, not access control: nothing in the database
  prevents a raw INSERT from creating a notification the user switched off.

10.7  THE TENANT BOUNDARY IS THE MAIN CONTROL
--------------------------------------------------------------------------------
  There is no role model and no permission check in the data layer
  (auth_user_groups and auth_user_user_permissions are always empty). All
  authorization is ownership: filter by user_id, always. The
  apps/users/tests/test_isolation.py suite exists specifically to prove that
  one user can never read another's jobs, resumes, applications or
  notifications.

      python manage.py sqlmigrate <app> <migration>

  The unrelated ai-job-agent/db.sqlite3 at the REPOSITORY ROOT is not this
  project's database. settings.py resolves BASE_DIR to backend/, so the root
  file (which contains only an empty auth_group) is a stray artefact.

11.2  FILE STORAGE IS NOT IN THE DATABASE
--------------------------------------------------------------------------------
  resumes_resume.file holds a RELATIVE PATH, not the document. The bytes live
  under MEDIA_ROOT (default backend/media/resumes/). This means:
    * A database restore does NOT restore a user's uploaded documents. Back up
      MEDIA_ROOT (or move to object storage) alongside the database.
    * settings_test.py redirects MEDIA_ROOT to a temp dir, so a test run never
      writes into the working tree.
    * MEDIA_URL is "/media/". In DEBUG Django serves it; in production
      Gunicorn has no front web server, so config/urls.py adds the static()
      route explicitly and the platform is expected to serve it properly.

11.3  SESSION AND LOG ROWS GROW UNBOUNDED
--------------------------------------------------------------------------------
  There is no scheduled purge. django_session accumulates rows until Django's
  own clearsessions runs, and users_securityevent is append-only with no
  retention policy. If either grows materially, add a management-command purge
  rather than assuming the platform will do it. Note that purging security
  events is a product decision (audit retention), not just housekeeping.

11.4  ROW-COUNT EXPECTATIONS
--------------------------------------------------------------------------------
  users_userprofile          at most 1 per user
  users_providercredential   at most N providers per user (currently gemini,
                             groq); all rows deleted on sign-out
  users_securityevent        unbounded, append-only
  jobs_job                   bounded by unique_job_url_per_user
  resumes_resume             unbounded; a master plus N tailored versions
  resumes_resumeprofile      at most 1 per resume
  applications_application   at most 1 per (user, job)
  automation_notification    bounded per (user, kind) ONLY where dedupe_key is
                             set; unbounded where it is blank
  automation_notificationpref. at most 1 per user (0 is valid and means
                             "all defaults on")

      Resume.objects.filter(user=request.user, is_master=True)

  Active applications, served by app_user_status_idx:

  Find users holding an encrypted provider key (row count only -- never
  select encrypted_key into a log or a response):

11.6  ONBOARDING CHECKLIST FOR A NEW TABLE
--------------------------------------------------------------------------------
  Adding a table to this project means answering all of these, because each is
  a rule the existing nine tables already follow:
    1. Does it carry user_id FK -> auth_user, ON DELETE CASCADE?  (If it is
       reachable from a user, yes. resumes_resumeprofile is the one exception,
       and it is deliberately reachable only through its parent.)
    2. Is the primary key an explicit BigAutoField, not a bare `id`?
    3. Does it have created_at (auto_now_add) and updated_at (auto_now) where
       "when did this last change" is meaningful?
    4. Does it need Meta.ordering so list endpoints are deterministic?
    5. Does anything in it have to be unique per user, and is that a
       composite UniqueConstraint rather than a bare unique?
    6. Are the read paths filtered by user_id, and is there an index that
       serves them?
    7. If it stores JSON, is the shape documented in Section 8, and does the
       READ path tolerate a malformed or absent payload?
    8. Does it hold anything a user would not want another user to see? If so,
       it needs the ownership column, not just a foreign key to it.

# Deployment

TailorUp is two deployables. They need different hosts.

```text
Vercel  ──────────────►  React SPA (static, serverless)
   │  HTTPS, VITE_API_URL
   ▼
Render  ──────────────►  Django API (gunicorn + Postgres)
```

---

## Why the backend cannot live on Vercel

Vercel functions run in stateless, short-lived containers. This project needs:

| Needs | Vercel provides |
| --- | --- |
| A persistent filesystem (SQLite, uploaded PDFs) | Ephemeral, wiped between invocations |
| Long-running requests (15s Greenhouse scrape) | Function timeout limits |
| Background work | None |

Putting Django here would appear to work, then silently lose users' accounts,
resumes, and jobs — and log everyone out constantly, because Django's default
session engine is database-backed.

Deploy the SPA to Vercel and the API to a stateful host.

---

## 1. Frontend → Vercel

**Project settings**

| Setting | Value |
| --- | --- |
| Root Directory | `frontend` |
| Framework Preset | Vite |
| Build Command | `npm run build` |
| Output Directory | `dist` |
| Node.js | 20 or newer |

**Environment variable**

```
VITE_API_URL=https://<your-render-host>/api
```

The trailing `/api` is required — the client appends `/auth/me/`, `/jobs/`, etc.

`frontend/vercel.json` already handles SPA fallback, so a hard refresh on
`/app/dashboard` serves `index.html` instead of a 404.

> Vercel auto-detection is not used here. With Root Directory set to
> `frontend`, the stray root-level `manage.py` and the empty root-level
> `requirements.txt` are never read. Those two files are leftovers from the
> original layout — the real ones are in `backend/`.

## 2. Backend → Render

`render.yaml` is a Render Blueprint, so the whole service is one click.

1. Push the changes to `main`.
2. Render Dashboard → **New** → **Blueprint** → select this repo.
3. Render provisions `tailorup-api` + `tailorup-db`, links them, and injects
   `DATABASE_URL`.
4. The start command runs `migrate` and `collectstatic` on every boot.

### Environment variables to set in the Render dashboard

| Variable | Value |
| --- | --- |
| `FRONTEND_ORIGIN` | `https://your-app.vercel.app` |
| `CSRF_TRUSTED_ORIGINS` | `https://your-app.vercel.app` |
| `CORS_ALLOWED_ORIGINS` | `https://your-app.vercel.app` |
| `ALLOWED_HOSTS` | your Render hostname, e.g. `tailorup-api.onrender.com` |

`SECRET_KEY` is auto-generated by the blueprint (`generateValue: true`).
`DEBUG` and `PYTHON_VERSION` are already set in `render.yaml`.

> Update all four variables **after** the first deploy, once you know the real
> hostnames. `FRONTEND_ORIGIN` is the important one — without it the SPA's
> session cookie is rejected by CSRF.

### What production mode changes

`settings.py` reads these from the environment, and when `DEBUG=False` it also
switches on SSL redirect, secure cookies, HSTS, and `X-Frame-Options: DENY`.
When `DATABASE_URL` is set, the database switches from SQLite to Postgres.
Static files are served by WhiteNoise; media is served by Django itself, since
Gunicorn has no web server in front of it.

### Uploads are ephemeral on the free tier

`MEDIA_ROOT` is on the container filesystem, so uploaded resumes are lost on
redeploy. Attach a persistent disk by uncommenting the `disk:` block in
`render.yaml` (requires a paid plan), or move resumes to S3-compatible object
storage. **Your database rows are safe either way** — only the PDF files are
at risk.

## 3. After both are live

1. Create the first admin: Render shell →
   `python manage.py createsuperuser` (then `/admin`).
2. Or just sign up at `/signup`, upload a PDF, and start analysing jobs.
